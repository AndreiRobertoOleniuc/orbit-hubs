# BadenConnect Prototype

Throwaway TS scripts validating the chunked-multi-vector retrieval design before porting to Spring Boot. Not a server, not an API — plain `tsx`-run files against a local Postgres + Ollama.

## File map

```
prototyping/
  package.json            top-level proto manifest
  tsconfig.json
  db/migrations/
    002_unified_chunks.sql        persons, publications, chunks, person_identities
                                  + backfill from companies.embedding
  src/lib/
    db.ts                 shared pg.Pool + vector literal helper
    embed.ts              ONLY caller of Ollama; passage/query role prefixes;
                          truncation fallback 1500 → 1000 → 600 chars
    chunks.ts             upsertChunks(): delete-by-source + batched INSERT in one tx
    chunk_text.ts         sliding window ~350 words, ~50 overlap, paragraph-aware
  src/ingest/

    website_batch.ts      CSV driver with progress bar, writes ingestion_report.json
  src/search/
```

## Run order

```bash
# 1. apply migration (assumes companies table already exists from lindasEmbedding/)
psql "$DATABASE_URL" -f db/migrations/002_unified_chunks.sql
# or:
npm run migrate

# 2. install deps (only first time)
npm install

# 3. ingest websites (idempotent — re-running replaces chunks per URL)
npm run ingest:websites

# 4. interactive search
npm run search
#    optional filter:
npx tsx src/search/search.ts --type=person
npx tsx src/search/search.ts --type=company

# 5. evaluation
npm run eval
```

## Design rationale

### Why chunked multi-vector per entity

Companies got away with one embedding per row because the LINDAS `zweck` field is a single short paragraph. People can't — a personal site is 4 000+ words spanning many topics. Embedding the whole concatenated text dilutes any one topic into noise; embedding paragraph-by-paragraph preserves topic-specific signal that the multilingual-e5 model can actually match against a focused query like "engineering management leadership observability."

The `chunks` table is **polymorphic by design** (no FK on `entity_id`, `entity_type` discriminator, `entity_id` is `TEXT` to bridge integer `companies.id` and UUID `persons.id`). This buys one unified retrieval query across companies, people, and (later) publications instead of three separate vector tables to UNION at query time. The trade-off is referential integrity is enforced in code, not the schema.

Aggregation is **max-pool over chunks**: an entity's score is the distance of its single best-matching chunk, not an average. Averaging penalises long profiles for having off-topic chunks; max-pool rewards them for having one strongly relevant one. This matches the product story — we're surfacing "the founder whose firmware repo mentions ESP32," not "the founder whose average paragraph is 0.4 similar."

### Why citations are first-class

Every chunk carries a `chunk_label` (human readable, surfaced as the "matched via …" line in the UI) and a `source_url` (clickable evidence). A chunk that can't be cited isn't worth storing — the UX promise of *"no percentage bars, only evidence"* depends on this. The eval queries verify entity-level retrieval; the search CLI prints the citation triple (`chunk_label`, `chunk_kind`, `source_url`) so retrieval quality can be eyeballed against rationale quality at the same time.

### Why plain HTTP, no headless browser

SPA-heavy personal sites (Bruno Simon's 3D portfolio, Dustin Brett's desktop-OS clone) return shells with no text — Readability extracts <200 chars and we log them as `empty`. Adding Playwright would cover them but doubles the dependency surface for sites that don't represent the target demographic (Swiss researchers and startup founders run blogs, not WebGL portfolios). Recording the blind spot honestly is more useful for the thesis than over-engineering around it.

### Why no HNSW yet

Brute-force `<=>` cosine on ~46k company chunks + ~100 person chunks runs in 200–500 ms end-to-end — fine for prototype eval loops. HNSW gets added before the formal benchmark numbers go into the Fachbeitrag, not before.
