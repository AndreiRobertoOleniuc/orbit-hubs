❯ What would this do?                                                                                                                                                               
                                                                                                                                                                                    
  BM25 + RRF                                                                                                                                                                        
  
⏺ BM25 = a classic lexical (keyword) ranker. For each query term it scores documents by:
  - how often the term appears in the doc (term frequency, with diminishing returns)
  - how rare the term is across the whole corpus (IDF)
  - normalized by document length
  
  So if you search Airflow dbt, BM25 surfaces docs that literally contain those rare tokens, ranked by how prominently. It has no idea what the words mean — but it's unbeatable
  when the user types a specific term that exists verbatim in the data. Postgres ships it via tsvector / ts_rank_cd, or you bolt on the pg_search / paradedb extension for proper
  BM25.

  Why combine with embeddings? They fail in opposite ways:
  - Embeddings: great at concepts ("jemand der Compliance-Themen versteht" → finds RegTech people even without the word "RegTech"). Bad at rare specific tokens — "dbt" gets blurred
   into "data infra". 
  - BM25: great at rare specific tokens. Bad at concepts — won't connect "Compliance" to "RegTech" unless the word is in the doc.

  Run both, fuse the rankings.

  RRF (Reciprocal Rank Fusion) = the simplest robust way to fuse rankings. For each doc, sum 1 / (k + rank_i) across the rankers (k usually 60). Whoever ranks high in either list
  wins; whoever ranks high in both dominates.

  score(doc) = 1/(60 + rank_bm25) + 1/(60 + rank_vector)

  Two nice properties:
  1. No score calibration needed — BM25 scores (0–20+) and cosine scores (0–1) live on totally different scales. RRF only uses rank position, so you never have to normalize.
  2. It's almost parameter-free. k=60 is the published default and rarely needs tuning.

  Applied to your eval: for the Data Engineering query, the vector list returned generic Cloud/DevOps people because no profile is a real Airflow/dbt specialist. BM25 over the same
   corpus would rank docs that literally mention "Airflow" or "dbt" (probably very few — which is correct, it'd expose that the data is thin there rather than hiding it behind
  plausible-but-wrong neighbors). RRF then surfaces whoever appears strongly in either list.

  It's also what the README pipeline already calls for — the "Hybrid Search (BM25 + pgvector)" + "Reciprocal Rank Fusion" boxes are exactly this. The scope weights (FHNW → Aargau →
   CH) would slot in as additional rankers in the same RRF sum.

❯ How could we add explainability to the matchees like why the person was matched in Version 6?                                                                                     

⏺ Three layers, roughly in order of cost. You'd usually stack at least two:
  
  1. Score decomposition (free, deterministic) — already half-built in v5. Carry through each leg's rank/score for each result and render them: "matched via dense rank #2 (cosine 
  0.86) + lexical rank #1 (BM25 12.3)". Tells the user which retrieval signal found this person. Useful for debugging and for trust ("we found them via keyword match, not just
  vibes").

  2. Lexical highlight (cheap) — Postgres' ts_headline() returns the description with <mark>…</mark> around the spans matching the tsquery. So for the Data Engineering query you'd
  literally see "…erfahrene Senior Data Scientist mit Schwerpunkt auf Predictive Maintenance…". Drop-in upgrade — same query, just wrap the select. Shows which words triggered the
  match. Doesn't explain semantic matches at all (the dense leg gets nothing), so pair it with #1.

  3. LLM rationale (the README's plan) — for the final top-K (say 5), call your local LLM with query + description + matched_tokens and ask for 1–2 sentences: "Diese Person passt, 
  weil…". This is the only layer that can explain semantic matches ("the query said 'Telco', Nicolas's profile says 'Swisscom' — same domain"). Slow (~1s/result with batiai/gemma4)
   and non-deterministic, but it's the user-facing rationale the product spec actually asks for. Cache by (query_hash, person_id) so repeat queries are free.

  Two harder additions worth knowing about:

  - Sub-document attribution — re-embed each sentence of the description and show which sentence had the highest cosine to the query. Tells you which part of the profile carried
  the match. Costs N extra embedding calls per insert (one-time at ingest if you store sentence vectors).
  - Counterfactual explainability — re-run retrieval with one signal removed (e.g. drop the lexical leg, or mask a token) and show how the ranking changed. Heavyweight, mostly an
  eval tool not a UI feature.

  My recommendation for v6: build #1 + #2 first (cheap, immediate, deterministic), then layer #3 only for the top-K to keep latency manageable. Want me to write it?

  3. Score decomposition — keep, but only in an internal /debug view for you + Luca. Useful for spotting when retrieval is suspicious; not shown to users.
