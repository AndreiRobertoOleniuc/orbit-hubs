❯ What would this do?                                                           
                                                                                
  BM25 + RRF                                                                    

⏺ BM25 = a classic lexical (keyword) ranker. For each query term it scores
  documents by:
  - how often the term appears in the doc (term frequency, with diminishing
  returns)
  - how rare the term is across the whole corpus (IDF)
  - normalized by document length

  So if you search Airflow dbt, BM25 surfaces docs that literally contain those
  rare tokens, ranked by how prominently. It has no idea what the words mean —
  but it's unbeatable when the user types a specific term that exists verbatim
  in the data. Postgres ships it via tsvector / ts_rank_cd, or you bolt on the
  pg_search / paradedb extension for proper BM25.

  Why combine with embeddings? They fail in opposite ways:
  - Embeddings: great at concepts ("jemand der Compliance-Themen versteht" →
  finds RegTech people even without the word "RegTech"). Bad at rare specific 
  tokens — "dbt" gets blurred into "data infra".
  - BM25: great at rare specific tokens. Bad at concepts — won't connect
  "Compliance" to "RegTech" unless the word is in the doc.

  Run both, fuse the rankings.

  RRF (Reciprocal Rank Fusion) = the simplest robust way to fuse rankings. For
  each doc, sum 1 / (k + rank_i) across the rankers (k usually 60). Whoever
  ranks high in either list wins; whoever ranks high in both dominates.

  score(doc) = 1/(60 + rank_bm25) + 1/(60 + rank_vector)

  Two nice properties:
  1. No score calibration needed — BM25 scores (0–20+) and cosine scores (0–1)
  live on totally different scales. RRF only uses rank position, so you never
  have to normalize.
  2. It's almost parameter-free. k=60 is the published default and rarely needs
  tuning.

  Applied to your eval: for the Data Engineering query, the vector list returned
   generic Cloud/DevOps people because no profile is a real Airflow/dbt
  specialist. BM25 over the same corpus would rank docs that literally mention
  "Airflow" or "dbt" (probably very few — which is correct, it'd expose that the
   data is thin there rather than hiding it behind plausible-but-wrong
  neighbors). RRF then surfaces whoever appears strongly in either list.

  It's also what the README pipeline already calls for — the "Hybrid Search
  (BM25 + pgvector)" + "Reciprocal Rank Fusion" boxes are exactly this. The
  scope weights (FHNW → Aargau → CH) would slot in as additional rankers in the
  same RRF sum.

❯ How could we add explainability to the matchees like why the person was       
  matched in Version 6?                                                         

⏺ Three layers, roughly in order of cost. You'd usually stack at least two:

  1. Score decomposition (free, deterministic) — already half-built in v5. Carry
   through each leg's rank/score for each result and render them: "matched via 
  dense rank #2 (cosine 0.86) + lexical rank #1 (BM25 12.3)". Tells the user
  which retrieval signal found this person. Useful for debugging and for trust
  ("we found them via keyword match, not just vibes").

  2. Lexical highlight (cheap) — Postgres' ts_headline() returns the description
   with <mark>…</mark> around the spans matching the tsquery. So for the Data
  Engineering query you'd literally see "…erfahrene Senior Data Scientist mit 
  Schwerpunkt auf Predictive Maintenance…". Drop-in upgrade — same query, just
  wrap the select. Shows which words triggered the match. Doesn't explain
  semantic matches at all (the dense leg gets nothing), so pair it with #1.

  3. LLM rationale (the README's plan) — for the final top-K (say 5), call your
  local LLM with query + description + matched_tokens and ask for 1–2 sentences:
   "Diese Person passt, weil…". This is the only layer that can explain semantic
   matches ("the query said 'Telco', Nicolas's profile says 'Swisscom' — same
  domain"). Slow (~1s/result with batiai/gemma4) and non-deterministic, but it's
   the user-facing rationale the product spec actually asks for. Cache by
  (query_hash, person_id) so repeat queries are free.

  Two harder additions worth knowing about:

  - Sub-document attribution — re-embed each sentence of the description and
  show which sentence had the highest cosine to the query. Tells you which part
  of the profile carried the match. Costs N extra embedding calls per insert
  (one-time at ingest if you store sentence vectors).
  - Counterfactual explainability — re-run retrieval with one signal removed
  (e.g. drop the lexical leg, or mask a token) and show how the ranking changed.
   Heavyweight, mostly an eval tool not a UI feature.

  My recommendation for v6: build #1 + #2 first (cheap, immediate,
  deterministic), then layer #3 only for the top-K to keep latency manageable.
  Want me to write it?

⏺ Partly. #3 is mandatory — the spec literally says "every match explains why 
  with cited sources" and "text rationale", that's the LLM rationale layer
  verbatim. But #1 as a user-facing signal collides with another explicit rule:
  "no percentage scores as primary signal". Scores belong in your internal
  eval/debug view, not the bulletin-board UI.

  The piece that's actually missing from #1 + #3 is source attribution — the
  spec says "cited sources" and "evidence-forward", which means each rationale
  sentence needs to point at the underlying source document it came from (this
  GitHub repo, that ORCID paper, that personal-site section), not just at the
  synthesized profile description. Right now your pipeline collapses everything
  into one paragraph before embedding, so that provenance is already lost — the
  LLM can fabricate plausible rationales but can't cite. To fix that you'd keep
  the per-source raw evidence alongside the profile and pass top-3 evidence
  snippets into the rationale prompt, then have the LLM quote/link them.

  So my recommendation for v6:

  1. LLM rationale — required, user-facing. Prompt it with query + profile 
  summary + top evidence snippets and ask for 2 sentences plus a citations list.

  descriptions, paper abstracts, website paragraphs), retrieve top-K snippets
  per matched person at query time (cheap second-stage similarity), feed them to
   the rationale prompt as the evidence to cite.
  3. Score decomposition — keep, but only in an internal /debug view for you +
  Luca. Useful for spotting when retrieval is suspicious; not shown to users.

   plumbing = score decomp + eval.

⏺ One search, not two — but with document types in the index, and the UI labels
  them. Here's the reasoning:

  The asymmetry that matters is supply vs. demand, not person vs. inserat. A
  Person profile and an "offering" inserat both represent capability supply. A
  "looking-for" inserat is demand. When Sarah Kovač types "Security Review JWT",
   she's expressing demand — she wants to see anything on the supply side that
  fits, and she doesn't care whether it's "Marc Hofer's permanent profile says 
  he does this" or "Marc Hofer posted an inserat last Tuesday saying he has 3 
  hours free". Both are useful. Two separate searches would force her to
  mentally merge two ranked lists, which is exactly the work the engine should
  do for her.

  Schema-wise, fold them into one searchable layer:

  documents
    id, type ('person' | 'offering' | 'request' | 'open_call'),
    owner_person_id,   -- inserate always belong to someone
    title, body,
    embedding, description_tsv,
    valid_from, valid_until, hourly_rate, scope_radius_km,
    created_at

  One index, one hybrid retrieval, one RRF fusion. At re-rank time you can apply
   type-specific weights:

  - An active "offering" inserat from 3 days ago is a stronger signal than the
  same person's static profile — it tells you they're free right now. Boost it.
  - A stale inserat (past valid_until) gets filtered or down-weighted.
  - A "looking-for" inserat also returned in a "looking-for" search is the
  cross-pollination case (Sarah finds someone else looking for the same thing →
  they could team up). Useful, but lower weight, and labelled differently in the
   UI.

  The reverse direction (matching people to inserate) is the same machinery.
  When Marc posts an offering, a background job embeds it and runs the same
  search, so other users whose queries or demand-inserate match get notified.
  That's how scenario 2 (researcher gets notified when KMU posts a need) works
  without a separate pipeline.

  Bottom line: one index, one query, one ranked result list — but the result
  list contains a mix of cards (person card vs. inserat card) with clear type
  labels, and the ranking respects type-aware weights. Two separate searches is
  the wrong default; it pushes integration work onto the user and breaks the
  "evidence-forward, quiet" UX the spec describes.

  One footnote: every inserat ultimately points at a person (the poster). So the
   rationale layer can — and should — fuse both: "Marc Hofer · Senior Security 
  Engineer at Helvetia. His profile lists JWT and OAuth, and he posted an 
  inserat 3 days ago offering 4h slots for security reviews this week." That
  combined evidence is stronger than either source alone, and it's only possible
   because they live in the same index.

⏺ Yes, that's the right shape. Two refinements worth knowing before you commit:

  1. Separate entities from documents. A Person can have many documents — their
  generated profile, each GitHub repo, each paper abstract, each personal-site
  section, each inserat they posted. Same for Companies (Handelsregister entry +
   website + posted positions). Modelling it as entities ↔ documents (1:N) gives
   you two big wins:

  - Per-chunk retrieval beats one giant blob. Right now Marvin's whole career is
   one 80-word paragraph competing in one embedding. If instead each of his
  repos + his rationale paragraph + his FHNW affiliation are separate documents,
   the chunk that matches the query wins — and you don't dilute his signal with
  unrelated text.
  - Source-level evidence becomes free. The LLM rationale can cite "GitHub repo
  rag-prototype" instead of "his description says…", because the matched
  document is a real artefact.

  entities                  documents
    id                        id
    type (person|company|     entity_id  ───► entities.id
          inserat)            doc_type (profile|repo|paper|
    display_name              site_section|inserat_body|...)
    owner_entity_id (NULL,    title, body
      used for inserate       embedding, description_tsv
      pointing at a person)   valid_from, valid_until
                              metadata (jsonb: stars, citations,
                                hourly_rate, scope_km, source_url)

  2. Pipeline stages — yours is right, just be explicit about what each does.

  query
    → embed (multilingual-e5)
    → retrieval:    dense top-N + lexical top-N
    → RRF fuse     (rank-only, no calibration needed)
    → deduplicate by entity_id     ← easy to forget, important
         (keep best-ranked doc per entity, attach others as evidence)
    → re-rank      (apply structured weights:
                      entity type, scope FHNW→Aargau→CH,
                      inserat recency / valid_until,
                      GitHub repo stars, paper citations, …)
    → top-K (5)
    → rationale    (LLM with query + entity card + cited documents)

  The dedup step is the one most people miss. Without it, a single popular
  person can take three of your five result slots because three of their
  documents matched. After dedup, those three documents become three citations 
  on one card, which is exactly what "evidence-forward" looks like.

  One pragma about the re-rank stage: keep it as plain weighted addition over
  signals you can inspect (recency, scope, stars, citations) — not a learned
  model — until you have user feedback to learn from. Each weight should be
  tunable from a config file. That way when Norbert says "FHNW results aren't
  showing up enough", you change a number, not retrain.

  So: yes, the structure works. The two adjustments are (a) split entity from
  document so one entity can have many evidence pieces, and (b) explicitly dedup
   by entity after RRF so the result list is 5 people/companies not 5 documents 
  that happen to belong to 2 people.

❯ Do DB Schema would be two Entries for the Core Match Making?                  

⏺ Yes — for the matchmaking core, two tables is exactly it: entities and
  documents. Everything else (users, auth, OAuth tokens, integration sync state,
   message threads, reaction logs, scope geo) lives around that core but isn't
  touched by the retrieval pipeline.

  The split:

  - entities — the things you can return as a result. Three subtypes: person,
  company, inserat. Each has identity, display name, owner reference (for
  inserate → owning person/company), lifecycle fields (created_at, valid_until
  for inserate).
  - documents — the things you actually search over. Per-source chunks with
  embedding + description_tsv + entity_id. Many-to-one back to entities.

  That's the whole retrieval surface. Hybrid search hits documents, fuses ranks,
   dedups by entity_id, returns entities. The re-rank weights pull from columns
  on both tables (entity type, inserat freshness, document type, source-specific
   metadata in a jsonb column).

  The one judgement call: are inserate entities or documents? I'd say entities,
  because they have their own lifecycle, users react to them, and a search
  result card for an inserat is a different UI than a card for a person. Their
  body text becomes a document attached to them. Same pattern as a Person who
  has multiple documents (profile + repos + papers): an Inserat entity has one
  document (the body) but could later have attachments.

  So: 2 tables for the core. The schema breathes from there.
