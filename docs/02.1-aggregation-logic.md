# 02.1 — Aggregation Logic (Spring Data JDBC + Spring Modulith)

> **Purpose.** Defines how Domain-Driven Design aggregates map onto the Orbit data model
> when persisted with **Spring Data JDBC** (not JPA) inside a **Spring Modulith**.
> This is a code-generation contract: each section states what is an aggregate root,
> what is a child collection, and what is referenced by id only. Follow it literally.
>
> **Authoritative against the live schema.** This version was reconciled with the actual
> codebase (`V1__orbit_v2_schema.sql`, existing `com.orbit.*` modules and DTOs). Where the
> earlier draft used placeholder types (`Long`, `BIGSERIAL`, `Profile`), this version uses
> the project's real conventions. See **§0.1 Conventions** and the migration history note.

---

## 0. First principles (read before generating any persistence code)

Spring Data JDBC is **not** an ORM in the JPA sense. There is:

- **no persistence context**, no dirty checking — nothing is saved unless you call `save()`;
- **no lazy loading**, no proxies — an aggregate loads **eagerly and whole**;
- **no `@OneToMany` / `@ManyToOne`** — relationships are expressed by aggregate *structure*;
- **delete-all-then-reinsert** semantics for `@MappedCollection` children on `save()`.

The aggregate rules below exist *specifically* to keep that behaviour cheap and correct.

### The three-way classification used throughout this document

| Class | Rule | Persistence shape |
|-------|------|-------------------|
| **Write side with invariants** | Cluster that must stay consistent together | **Aggregate root** + `@MappedCollection` children |
| **Read side / projections / AI** | Cross-cutting, no invariant to protect | **Native SQL → DTO/record** (`JdbcClient`), no `CrudRepository` |
| **Stateless reactions / services** | Function-like, owns no persistent cluster | **Service**, no aggregate (optional module-private outbox only) |

### 0.1 Conventions (project-wide — reconciled with live code)

These override the placeholder choices in the earlier draft.

| Topic | Rule |
|-------|------|
| **IDs** | **`String`** for all domain aggregates. The v2 schema uses human-readable slug `text` PKs (`per-marc-hofer`, `req-lisa-embedded`, `gh-mhofer-oauth21-migration`). **Exception:** `Distribution` uses **`Long`** because `request_distributions.id` is `bigserial` (synthetic internal row). |
| **Aggregate class names** | **Match the table name:** `Entity`, `Document`, `Request`, `Distribution`. Do **not** name the supply aggregate `Profile` — `profile` is overloaded (public page / supply side) and `users` already exists as the auth account. |
| **API / DTO names** | May keep domain language (`ProfileDto`, `RequestDto`) even though the aggregate class is `Entity`. The API surface and the domain class names are allowed to differ. |
| **Inside an aggregate** | Full objects via `@MappedCollection`. |
| **Across aggregates** | Plain **`String` id field** (e.g. `ownerEntityId`), **not** `AggregateReference`. Schema stores raw `text` FK columns; `AggregateReference` adds ceremony for little gain at `String` ids. May be introduced later without a schema change. |
| **Read side / search / vectors** | `JdbcClient` + immutable records. Never a `CrudRepository<Root>`. |
| **Stateless modules** | Services only; no aggregates (optional module-private outbox for reliability). |
| **Vector dimension** | `vector(1024)` per the live schema (not 1536). Keep identical across `documents`/chunk storage and `requests`. |

### The two golden rules

1. **Inside an aggregate → full objects. Across aggregates → id only** (plain `String`).
2. **One aggregate lives entirely inside one Modulith module.** Cross-module access is an
   id-based read or a published-interface call (e.g. `ProfileQuery`, `RequestQuery`) — never
   object-graph traversal. This is what stops JPA-style association leaks across module walls.

## 1. Module-by-module verdict (matches live `com.orbit.*` packages)

| Module (`com.orbit.…`) | Aggregate? | What it owns |
|------------------------|-----------|--------------|
| `request` | **Yes** | `Request` root (+ `request_transitions` children); `Distribution` is a **separate** root |
| `profile` | **Yes** | `Entity` root (+ `availability`, `entity_tags` children); `Document` is a **separate** root (+ chunks) |
| `discovery` | **No** | Read models / projections via native SQL (pgvector). Owns no tables. |
| `embedding` | **No** | Stateless `embed(text, kind) -> vector`. Owns no table. (open module) |
| `onboarding` | **No** | Pipeline (Zefix → entity). Writes into `profile` via its module API. |
| `contact` | **No** | Stateless one-time email hand-off (`contact_handoffs` is a log, see §5). |
| `notification` | **No** | Stateless fan-out on distribute/contact. |
| `auth` | **No** | Support module. Publishes `CurrentUser`. No domain aggregate. (open module) |

> Module boundaries are already enforced (closed by default; `auth` and `embedding` open).
> `discovery` already declares it owns no tables. `ProfileQuery` + `JdbcProfileQuery`
> already demonstrate the published-read-interface pattern — `RequestQuery` should follow it.

## 2. `request` module

### 2.1 `Request` — aggregate root (with `request_transitions` children)

**Invariant:** `status` must always be consistent with the latest transition; illegal
transitions (e.g. from a terminal state) must be rejected. Because that rule spans the
root and its history, transitions are **children**, not their own aggregate.

```java
@Table("requests")
public class Request {
    @Id private String id;                 // slug PK, e.g. "req-lisa-embedded"
    private String ownerEntityId;          // cross-aggregate → plain String id
    private RequestStatus status;
    private Instant createdAt;
    // request-side embedding lives directly on this table (see §6)

    @MappedCollection(idColumn = "request_id", keyColumn = "seq")
    private List<RequestTransition> transitions = new ArrayList<>();

    public void transitionTo(RequestStatus next, String actorUserId, String note) {
        if (!status.canMoveTo(next)) throw new IllegalStateTransitionException(status, next);
        transitions.add(new RequestTransition(status, next, actorUserId, note, Instant.now()));
        this.status = next;
    }
}
```

```java
public record RequestTransition(RequestStatus from, RequestStatus to,
                                String actorUserId, String note, Instant at) {}
```

`request_transitions` has **no independent identity** — rows only make sense inside a
`Request` and are deleted with it.

### 2.2 `Distribution` — separate aggregate root (referenced by `requestId`)

**Decision:** distributions have their **own lifecycle** — queried independently
("all distributions awaiting response"), acted on by recipients, and they drive the
`notification` fan-out ("on distribute"). That independent identity makes them a
**separate aggregate**, not a child of `Request`.

```java
@Table("request_distributions")
public class Distribution {
    @Id private Long id;                    // bigserial — synthetic internal row
    private String requestId;               // cross-aggregate → plain String id
    private String entityId;                // the notified profile — cross-aggregate, plain id
    private String reason;                  // visible "Verteilt, weil..." text (02 §2)
    private String[] matchedTags;           // tags that caused the match (text[])
    private Instant createdAt;
}
```

> **Field names match `02`'s `request_distributions` columns** (`entity_id`, `reason`,
> `matched_tags`) — this is a *who-was-notified-and-why* record, not a stateful workflow row.
> If distributions later need a per-recipient response state (e.g. `RESPONDED`/`DECLINED`),
> add a `status` column to the schema first (see §8 open item), then to this class.

> **Why not a child:** as a `@MappedCollection` on `Request`, every `request.save()` would
> delete+reinsert all distributions, and you could not query/act on one without loading the
> whole request. Both contradict its actual usage.

### 2.3 Repositories (in `request/internal`)

```java
interface RequestRepository extends CrudRepository<Request, String> {}
interface DistributionRepository extends CrudRepository<Distribution, Long> {
    List<Distribution> findByRequestId(String requestId);
    List<Distribution> findByEntityId(String entityId);   // "where was I notified?"
}
```

Plus fill in **`RequestQuery`** (published read contract for `discovery` / `contact`),
backed by a `JdbcRequestQuery` using `JdbcClient` — mirror of `ProfileQuery`/`JdbcProfileQuery`.

## 3. `profile` module

### 3.1 `Entity` — aggregate root (table: `entities`)

`Entity` holds the supply-side person/firm data plus **small, fixed-cardinality** children
that share its consistency rules: `availability` (1:1) and `entity_tags` assignments.
These stay as children because they are few and always edited together with the entity.

```java
@Table("entities")
public class Entity {
    @Id private String id;                 // slug PK, e.g. "per-marc-hofer", "firm-trafosoft"
    private String userId;                 // cross-aggregate → auth user, plain String id
    private String displayName;
    // ... supply fields

    @MappedCollection(idColumn = "entity_id")
    private Availability availability;      // 1:1 value object (entity_id is PK on that table)

    @MappedCollection(idColumn = "entity_id")
    private Set<EntityTag> tags = new HashSet<>();   // assignments owned by the aggregate
}
```

```java
public record Availability(boolean openForRequests /* + window fields if any */) {}
public record EntityTag(String tagSlug) {}   // references the global tags vocabulary by slug
```

> **`availability`** has no independent lifecycle in v2 (it's the "Offen für Anfragen"
> toggle), so it stays a 1:1 child. Promote to its own aggregate only if it later grows
> independent queries/lifecycle.

> **Documents are NOT here.** See §3.2.

### 3.2 `Document` — separate aggregate root (with chunk children)

**Decision:** an entity can own **many, high-variance** documents, and each document is
**chunked** for embeddings — a scientific paper ≈ 100 chunks, a personal website ≈ 2 chunks.
If documents/chunks were children of `Entity`, every `entity.save()` would delete+reinsert
up to ~100 chunk rows — the exact anti-pattern Spring Data JDBC's delete-all-reinsert
semantics punish. Therefore:

- `Document` is its **own aggregate root**, referenced by `entityId` (plain `String`).
- chunks are `@MappedCollection` children of `Document`, so rewrites scope to one document.
- the embedding **vector lives on the chunk row** (`vector(1024)`).

```java
@Table("documents")   // citation metadata only — text/vector live on the chunks
public class Document {
    @Id private String id;                 // slug PK, e.g. "gh-mhofer-oauth21-migration"
    private String entityId;               // cross-aggregate → plain String id
    private String sourceType;             // github_repo | website_page | publication | ...
    private String sourceUrl;
    private String sourceLabel;            // footnote label shown in UI
    private String textHash;               // skip re-chunk/re-embed if unchanged
    private Instant fetchedAt;

    @MappedCollection(idColumn = "document_id", keyColumn = "chunk_index")
    private List<DocumentChunk> chunks = new ArrayList<>();
}
```

```java
@Table("document_chunks")   // child of Document; composite PK (document_id, chunk_index)
public class DocumentChunk {
    private String text;         // cleaned slice, ≤ ~4000 chars
    private float[] embedding;   // vector(1024), e5-large "passage:" prefix
    // chunk_index supplied by keyColumn; tsv is GENERATED in the DB
}
```

> **Schema state:** `document_chunks` is introduced by the AP8 migration `V4__document_chunks.sql`
> (creates the table, moves `embedding`/`tsv` off `documents`, backfills one chunk per existing
> document). See `02_data_model_and_api.md` §0 and §2. Generate against this shape, not the
> pre-V4 whole-document layout.

### 3.3 Repositories (in `profile/internal`)

```java
interface EntityRepository   extends CrudRepository<Entity, String> {}
interface DocumentRepository extends CrudRepository<Document, String> {
    List<Document> findByEntityId(String entityId);
}
// keep ProfileQuery / JdbcProfileQuery as the published read contract
```

### 3.4 Tags vocabulary (lookup, not an aggregate)

The global `tags` table is a shared vocabulary — it belongs to **no** aggregate. Assignments
(`entity_tags`, `request_tags`) are owned by their respective aggregates as `@MappedCollection`
children (`EntityTag`, `RequestTag`). A thin repository may serve the vocabulary:

```java
interface TagRepository extends CrudRepository<Tag, String> {}   // global lookup only
```

## 4. `discovery` module — NO aggregate (read side)

Search, similarity ranking, and rationale are **projections** across entities, documents and
requests. They protect no invariant. **Do not** route them through `CrudRepository` returning
aggregate roots.

- Use `JdbcClient` (the existing pattern), or `@Query` with **native SQL** — pgvector
  similarity is not expressible in JPQL anyway.
- Return **read-model records** (`SearchResultDto`, etc.), never `Entity`/`Document` aggregates.

```java
public record SearchResultDto(String entityId, String documentId, int chunkIndex,
                              String snippet, double score) {}   // String ids, not UUID

// native pgvector similarity → projection, not an aggregate
// SELECT ... 1 - (embedding <=> :queryVec) AS score
// FROM document_chunks dc JOIN documents d ON d.id = dc.document_id
// ORDER BY embedding <=> :queryVec LIMIT :k
```

`RationaleService` (lazy) composes read models + calls `embedding`; it persists nothing.

## 5. `embedding`, `onboarding`, `contact`, `notification` — NO aggregate

- **`embedding`** — stateless. `EmbeddingService.embed(text, kind) -> float[]`, vendor
  (OpenAI/Ollama) behind one interface. Storage is owned by `documents`/`document_chunks`
  and `requests`, never by this module.
- **`onboarding`** — pipeline. Reads Zefix, **writes into `Entity`/`Document` via the
  profile module's API**. Owns no aggregate.
- **`contact`** — stateless one-time email hand-off. `contact_handoffs` is an append-only
  **log** of hand-offs, not a domain aggregate with invariants; treat it as a module-private
  write log (a tiny root is acceptable, but it has no children and no cross-aggregate rules).
- **`notification`** — stateless fan-out on distribute/contact. Optional module-private
  outbox only, justified by delivery reliability, not by DDD modeling.

---

## 6. Embeddings & pgvector — placement contract

**Vectors live on the table that owns the text being embedded.** Dimension is **`vector(1024)`**.

| Text source | Vector column location | Owning aggregate |
|-------------|------------------------|------------------|
| Document chunks (supply) | `document_chunks.embedding` (one vector per chunk) | `Document` |
| Request content (demand) | `requests.embedding` (request text is **not** chunked — it's short) | `Request` |

The `embedding` module computes the vector; it is **written by** `profile`/`request` when
text is ingested/changed, and **read by** `discovery` via native SQL. `embedding` stores nothing.

## 7. Code-generation checklist (apply per entity)

1. **Invariant spanning parent + children?** → children `@MappedCollection`, parent is root.
   (`Request`+transitions; `Entity`+availability/tags)
2. **Own lifecycle / queried or acted on alone?** → its **own** root, referenced by id.
   (`Distribution`, `Document`)
3. **High / unbounded child cardinality?** → split into own aggregate so `save()` doesn't
   rewrite the whole collection. (`Document` out of `Entity`; chunks stay under `Document`)
4. **Cross-aggregate link?** → **plain `String` id** column (e.g. `ownerEntityId`). Not an
   embedded object, not `@ManyToOne`, not `AggregateReference` (by project convention).
5. **Read / projection / similarity?** → `JdbcClient` + DTO record. Not a `CrudRepository<Root>`.
6. **Stateless reaction?** → service, no aggregate (optional module-private log/outbox).
7. **Module boundary:** every root + children sit in one module; inbound refs are by id;
   cross-module reads go through the published `*Query` interface.
8. **IDs:** `String` everywhere except `Distribution` (`Long`, bigserial).
9. **Class name = table name:** `Entity`, `Document`, `Request`, `Distribution`.
